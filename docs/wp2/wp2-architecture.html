DAQ Agent Architecture

A read-only, natural-language assistant for shift operators over the five TDAQ live runtime services: Run Control, Process Management, Configuration (OKS), Information Service and Error Reporting. Every design decision below names the evidence behind it.

  • 5 service agents + 1 orchestrator
  • MCP agent-to-service protocol
  • Read-only by construction
  • Local open-weights model
  • 14 design decisions
  • Evidence base: 52 peer-reviewed sources, 5 preprints or talks (flagged)

One query, end to end

"Why did TileCal stop?"

WP1 showed that no single service can answer this. The useful answer comes from noticing that two services report the same word with different meanings.

  1. RouteOrchestrator sees a cross-service diagnosis and plans RC + PMG in parallel.
  2. Resolve"TileCal" → controller name and PMG process handle via resolve_identifier.
  3. RetrieveRC agent reads RCStateInfo; PMG agent reads process data, both via webis_server.
  4. TypeSemantic layer wraps each value with its vocabulary.
    rc.fsm: INITIAL
    "not configured for a run" · age 41 s
    pmg.process: RUNNING
    "OS process alive" · age 5 s
  5. CompareOrchestrator sees two consistent readings of two different things, not a contradiction.

Answer: TileCal did not stop. It never finished starting: the process is alive and growing in memory, but the controller never left INITIAL. Hung startup, not a crash, so the remedy differs.

Without layers L3–L4, the model receives two bare state strings and reports either "running" or "in INITIAL". Building the agent both ways is the core experiment (see Evaluation).

Design decisions

Fourteen decisions and their evidence

Each decision lists the evidence for it and the main alternative it rules out. Bracketed numbers point to the reference list; preprints and talks are tagged there.

Scope

D1

Read-only diagnostic assistant. Humans decide and act.

Why
Agents remain weak at end-to-end remediation, while operator-assist systems have shown measurable gains in production. TDAQ already automates recovery through CHIP.
Evidence
  • Agents resolve 11.4% of real SRE scenarios [6]; best RCA agent solves 11.34% [7].
  • Operator-assist deployed 10 months at Alibaba: time to root cause −20.5% [8].
  • The ATLAS-wide assistant effort keeps decisions human-driven [3].
Rejected
Autonomous mitigation as in [9], [10]. The effect taxonomy (D7) leaves room to add it later.

Agents and orchestration

D2

One agent per service behind an orchestrator (5 + 1)

Why
Each agent sees a small tool set and one vocabulary. Failures stay isolated and can be attributed to one service.
Evidence
  • Tool retrieval degrades on large tool sets and lowers task pass rate [11].
  • Orchestrator routing to per-team agents in production: triage accuracy up to 97%, time-to-engage −91% [12].
  • Specialised agents reduce context-switching errors [13]; hub-and-spoke isolation blocks cross-app attacks [14].
  • Same pattern at a light source [4] and at CMS [15].
Rejected
One assistant holding every tool, as in GAIA [2]. That suits one control system, not five services with colliding vocabularies.
D3

Star topology with a fixed, hand-designed workflow

Why
Agents never talk to each other directly. On a live system, a predictable and auditable path is worth more than benchmark gains.
Evidence
  • Coordination topologies (star, chain, tree, graph) compared in [16].
  • Dense agent chatter is costly: pruning communication cut tokens by up to 95% [17].
  • State-machine orchestration of specialised agents [9]; practitioners report successful systems use explicit structure [18].
Rejected
Automatically searched workflows and topologies [19], [20], [21]. They improve benchmarks but produce designs that change and are harder to certify.
D4

Orchestrator plans; service agents execute

Why
Simple questions go to one agent. Compound questions are decomposed, sent out in parallel, and composed.
Evidence
  • Planner/executor separation: 57.58% on WebArena-Lite [22].
  • Plan-first orchestration ran multistage experiments on a production accelerator [4].
  • Complexity check → decompose → route to per-source MCP agents [23]; query-dependent routing at 6–45% of the inference cost [21].
D5

ReAct inner loop with a round cap and explicit stop rules

Why
ReAct is the standard tool-use loop, but it has no stopping rule of its own.
Evidence
  • Reasoning interleaved with tool actions [24].
  • MCP-Bench caps the plan-execute-observe loop at 20 rounds [25].
  • In 1,642 multi-agent traces, step repetition (15.7%) and missing termination awareness (12.4%) are top failure modes [26].

Protocol and safety

D6

MCP as the agent-to-service protocol

Why
One protocol for five services. Its three primitives fit TDAQ: tools for live reads, resources for static OKS configuration, prompts for shifter procedures.
Evidence
  • MCP architecture, lifecycle and ecosystem analysed in [27]; specification [28].
  • Top models exceed 98% schema compliance across 28 MCP servers [25]; MCP-mediated evaluation methodology [29].
  • Schema-bound MCP for scientific instruments [30]. Archi at CMS does not use MCP [15].
Rejected
Bespoke per-subsystem integrations, as in [15].
D7

Closed tool registry, read-only by construction

Why
Safety is enforced by the server and the transport, not by the prompt. Tools carry an effect class; only read and rate-limited read-heavy are exposed.
Evidence
  • Poisoned tool metadata succeeds 72.8% of the time against o1-mini across 45 real servers [31].
  • MCP threat taxonomies: 16 scenarios [27]; STRIDE/DREAD on 7 clients [32]; multi-turn attacks [33]; contextual integrity [34].
  • WP1: webis_server is read-only by default; link_client creates server state; provider::command is a hidden mutation.
D8

Service text is data, never instructions

Why
ERS messages and process logs are free text written by thousands of applications. They reach the model only as quoted, length-bounded fields and cannot select tools.
Evidence
  • Observation prompt injection reaches 84.3% average attack success; current defences are weak [35].
  • Masked re-execution defence [36] is the fallback if raw text must be shown.
  • WP1: procFiles returns unbounded production text.

Grounding and knowledge

D9

Semantic mapping layer between tools and agents

Why
RC and PMG share six state tokens with different meanings. Schema validation catches malformed values; it does not catch a well-formed value with the wrong meaning. This layer types every value by vocabulary before the model sees it.
Evidence
  • Making expert knowledge a first-class input reached AC@5 of 90% on real OS failures [37].
  • Structured knowledge grounding improves faithful reasoning [38]. It grounds facts, not colliding vocabularies.
  • Unfamiliar real schemas drop agent success from 91.2% to 21.3% [39].
  • Gap: none of the 60 screened peer-reviewed papers addresses state-vocabulary collision across services.
Includes
Vocabulary registry, identifier resolution, derived quantities, source precedence, staleness rules, and a collision test in CI.
D10

Provenance envelope with a mandatory not_answered field

Why
A wrong answer at night costs more than no answer. Abstention has to be enforced by the output schema, because prompting does not reliably produce it.
Evidence
  • Reasoning fine-tuning degrades abstention by 24% on average; system prompts help but do not fix it [40].
  • Explicit "defer / clarify" actions reduce tool hallucination [41]; function-calling benchmarks now score abstention [42].
  • Coverage@Acc and Abstain ECE make abstention measurable [43].
D11

Documents through RAG; live state only through tools

Why
Procedures and manuals answer "how do I"; only live tools answer "what is the state now". Mixing them yields answers about TileCal taken from a wiki page.
Evidence
  • RAG for knowledge-intensive tasks [44]; a CERN documentation chatbot already exists [45], so this project is the live-data complement.
  • SOP-guided RCA raised localisation accuracy from 35.5% to 64.0% [46]; documents converted to workflows beat baselines on OpenRCA [47]; reusable workflows +24.6% / +51.1% [48].
So
Shifter procedures become MCP prompts that agents can discover.

Infrastructure

D12

Local open-weights model, treated as a swappable part

Why
Operational data stays on site. The model sits behind one interface, so 2–3 models can be compared.
Evidence
  • Open-weights gpt-oss-120b scores 0.692 vs o3 0.715 on MCP-Bench [25].
  • Privacy-preserving log parsing with an 8B open model [49]; on-premises stack at a production accelerator [4].
  • Local Mixtral at DESY [2]; open-source LLM in the ATLAS effort [3].
D13

Replay harness with fault injection, sharing the tool schema

Why
Repeatable tests without Point 1, and a regression suite that runs on every change.
Evidence
  • Fault injection plus telemetry export for agent evaluation [5]; 735 reproducible failure cases [50].
  • Curated initial state with programmatic verification [51].
  • Simulator sharing the schema layer with live adapters [30].
D14

Per-agent, per-step trace log

Why
When a multi-agent answer is wrong, we need to know which agent and which step caused it.
Evidence
  • Automatic failure attribution is hard: best method reaches 53.5% agent-level and 14.2% step-level accuracy [52]. Logs must make it explicit.
  • Attribution and audit infrastructure for agents [53]; event-stream design [54].

How it will be judged

Per-agent report cards, plus one ablation

Five separate report cards, one per service agent, using established metrics where they exist. The central experiment builds the system twice: once with raw records and a prose system prompt, once with layers L3–L4. Both run on a vocabulary-collision test set.

DimensionMetricBasis

Realistic expectations. Comparable benchmarks report under 50% task success [55], 11–12% on root-cause analysis [7], [6], and around 30% on long workplace tasks [57]. Targets should be set against these figures.

Positioning

What is adopted and what is new

Adopted from the literature

  • ReAct agents with RAG for documents [24], [44]
  • Orchestrator over specialised agents [12], [4], [15]
  • MCP as the tool protocol [27], [30]
  • Local open-weights inference [2], [49]
  • Replay and fault-injection evaluation [5], [51]

Contribution of this project

  • Semantic vocabulary collision as a named failure mode for agents on mature, heterogeneous facilities, with a layer that makes it unrepresentable (D9–D10).
  • The first MCP framework over the five TDAQ live services, and MCP over distributed multi-service runtime infrastructure in general.
  • A generalisation ledger: how much of the framework survives reuse across five services, with predictions registered before WP3.
