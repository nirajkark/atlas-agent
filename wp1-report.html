01

What WP1 found

WP1 asked four blocking questions. All four are now answered against source rather than against secondary literature — and three of the four answers contradict the working draft.

The working draft described Run Control using a state model drawn from the publicly citable ATLAS papers, which are largely 2003–2013. That model is obsolete. The FSM was rewritten in 2012–2014, and the current implementation shares only three state names with the one in the literature. Any agent built on the published description would have produced confidently wrong answers about the state of a live partition.

This is the single most consequential outcome of WP1, and it generalises: for a system of this age, the citable documentation and the running code have diverged. The methodology in §2 exists to make that divergence detectable rather than accidental.

F1 · RESOLVED

CONNECTED exists, and sits between CONFIGURED and RUNNING

The open question in the draft is settled. CONNECTED is a real state, entered from CONFIGURED by CONNECT, and left towards RUNNING by START.

F2 · CORRECTION

BOOTED, READY and PAUSED do not exist

Nor do boot, prepareForRun, pause or resume. The draft's six-state model is the pre-2012 FSM. The current FSM has eleven states.

F3 · CORRECTION

Stopping is a six-step ordered drain, not one transition

STOP expands into six sub-transitions through five intermediate states, draining the dataflow in a fixed order. A partition mid-stop is in a named state, not "stopping".

F4 · CORRECTION

ERROR is not a state — it is an orthogonal flag

The FSM has no error state. Error is carried as a separate list of reasons alongside the state. "Which controllers are in ERROR?" is not a state query.

F5 · RESOLVED

The IS classes are documented in-repo after all

The draft assumed IS class names required a live partition. PMGPublishedProcessData and PMGPublishedAgentData ship as an OKS schema in ProcessManager; the RC classes are recoverable from the publisher source.

F6 · CORRECTION

The RC CORBA interface is rc::commander

Not rc::controller. And Controllable is a C++ base class, not an IDL interface — it never appears on the wire.

F7 · CORRECTION

The PMG Handle carries an optional port

The grammar is pmg://host[:port]/partition/app/id. A parser built to the draft's four-field form will mis-parse any handle that names a non-default port.

F8 · NEW RISK

Three state vocabularies collide by name

RC FSM state, RC supervision status and PMG process state share six token names with different meanings. RUNNING means two unrelated things. This is the project's central safety problem — see §5.

What this changes about the project

F8 reframes the contribution. Before WP1, the semantic mapping layer was a tidiness measure — a way to avoid five agents each writing their own IS reader. After WP1 it is the load-bearing safety component: it is the only place where the three RUNNINGs can be told apart, and an agent that skips it can tell a shifter a detector is running when its processes are alive but taking no data. The architecture paper should be built around this, not around code reuse.

02

Method and evidence rules

WP1 is a verification exercise, so its method has to be stated as precisely as an experimental one. Otherwise the next person cannot tell which claims are load-bearing.

2.1 Source-of-truth ordering

Every factual claim in this report is assigned to one of four evidence classes, and the class is recorded. Where classes disagree, the higher class wins and the disagreement is reported as a finding rather than silently resolved.

Table 1 Evidence classes, in decreasing authority
ClassSourceAuthorityUsed in this report for
E1Implementation sourceDefinitiveState and command enumerations, transition tables, IDL surfaces, IS attribute names, identifier grammars
E2In-repo schema & IDLDefinitiveIS class definitions and attribute types, exception vocabularies
E3In-repo doc commentsCorroboratingIntent and semantics of a field. Verified against E1 before use — two disagreements found
E4Published papers, TWikiUntrustedHistorical context only. Never used to establish a current fact

The demotion of E4 to untrusted is deliberate and is itself a WP1 result. The draft's FSM came from E4 and was wrong in five of six state names. For a system whose most citable architecture papers predate the current implementation by a decade, treating the literature as authoritative is a methodological error, not a shortcut.

2.2 Reproducing this study

The draft anticipated that the repositories would be hard to reach — GitLab renders file contents client-side, so HTTP fetch returns an application shell rather than source, and the associated TWikis are SSO-gated. Both observations are correct, and both are avoidable: the repositories are Apache-2.0 and clone anonymously over HTTPS without CERN credentials. No SSO, no Point 1 access, and no TDAQ release install is needed to reproduce every claim in §§3–6.

# Everything in this report is derivable from these two clones.
git clone --depth 1 https://gitlab.cern.ch/atlas-tdaq-software/RunControl.git
git clone --depth 1 https://gitlab.cern.ch/atlas-tdaq-software/ProcessManager.git

Consequence for the WP1 budget

The draft budgeted time for credential acquisition before the service study could begin. That dependency is removed for the data-model work: the full RC and PMG data models are recoverable offline, today. Credentials remain on the critical path only for Tier 2 — see §7 — which means WP1's remaining unknowns are now about access, not about structure.

2.3 What "verified" means here

A state, command, attribute or method is called verified when it was read from a declaration in source (E1/E2) and, where a string representation exists, cross-checked against the mapping that produces it. Every state and command name in §3 was checked both ways: the enumerator exists, and its externally visible string is confirmed. This matters because the agent will match on strings, not enumerators, and a name that exists in C++ but is published differently would break silently.

03

Run Control: the verified data model

Run Control enforces uniform state across the thousands of applications that make up a data-taking partition. For agent purposes it is three things: a tree, a state machine, and a status record published to the Information Service.

3.1 The control tree

The draft's description of the hierarchy is accurate and survives verification. A Root Controller supervises the partition; Segment Controllers beneath it group detector subsystems as defined by OKS; leaf nodes are controlled applications. Commands propagate down; each controller forwards a transition to its children, awaits their asynchronous replies, aggregates what they report, and only then updates itself.

One structural detail matters for the agent and is not obvious from the architecture papers: the Root Controller runs a different state machine from everything below it. The FSM is a template parameterised on its initial state, and only two initial states are legal — NONE for the Root Controller, INITIAL for every child controller and leaf application. The Root Controller's table includes transitions to and from NONE; a child's table does not contain them at all.

Why the agent must care

"Which transitions are legal from here?" — one of the RC agent's in-scope questions — has different answers for the Root Controller and for a segment controller in the same state. SHUTDOWN and RELOAD_DB exist only at the root. An agent that models one FSM for all nodes will offer illegal transitions on four-fifths of the tree.

3.2 The finite state machine, verified

Trap: RELOAD_DB is deferred, not refused

Outside NONE, RELOAD_DB is queued rather than rejected, in a deferred queue holding exactly one event. An operator asking "did my reload take effect?" can be told "the command was accepted" and have that be true while nothing has happened yet, possibly for hours. The RC agent must distinguish accepted, deferred and applied. This is the clearest case in either service where the honest answer is three-valued and the tempting answer is binary.

Two documentation defects found in-repo

Recorded because they will mislead anyone repeating this study, and because they justify the E1-over-E3 rule in Table 1.

  • EOR alias mismatch. The header comment states that EOR (end of run) aliases STOPRECORDING. The implementation defines it as STOPARCHIVING — the last drain step, not the fourth. The implementation is authoritative; an agent that resolved "end of run" via the comment would report the run as ended two states early.
  • Stale BOOTED reference. A worked example in the path-finding code still narrates a route through BOOTED, a state that no longer exists in the enumeration. This is a fossil of the pre-2012 FSM, and it is almost certainly the proximate source of the draft's state list.

3.3 Error and busy are orthogonal to state

The draft says a failing node "marks ERROR". No ERROR state exists. What exists instead is richer and must be modelled separately from the FSM:

errorReasons
A list of strings. Empty means healthy. Non-empty means the node is in error while still occupying a normal FSM state. This is the actual answer to "which components are in error".
badChildren
A list of child names the node considers unhealthy. This is how error localises down the tree, and it is what lets the agent answer "the segment is unhealthy because of these two applications" rather than just "the segment is unhealthy".
busy
Boolean. The node is executing a command. Distinct from transitioning.
transitioning
Boolean. The node is mid-transition, so its reported state is stale by construction.
fault
Boolean. Internal error of the controller itself, as opposed to a problem it is reporting about its children.
fullyInitialized
Boolean. The node has completed its handshake with Process Management. See §6 — this is the RC/PMG join in the data model.

The command-refusal vocabulary confirms the same separation from the other direction. When a command is rejected the failure carries a reason drawn from four values: BUSY, NOT_ALLOWED (refused by the Access Manager), IN_ERROR, and UNEXPECTED. Busy and in-error are distinct refusal causes, which they could not be if error were a state.

Design consequence — RC agent response contract

The draft's response contract required partition, controller name, timestamp, and a distinction between own state and subtree state. WP1 adds a hard requirement: state must never be returned alone. The minimum honest unit is {state, transitioning, busy, errorReasons, badChildren, timestamp}. A node reporting RUNNING with two entries in errorReasons is a normal and important condition, and any contract that lets the agent return just RUNNING makes that condition unreportable.

3.4 The CORBA surface

Run Control exposes a single operator-relevant interface, rc::commander — not rc::controller as the draft states (F6). Its methods split cleanly for the read-only scope:

Table 4 rc::commander — the Tier 3 surface, classified

Both read methods return an encoded string rather than a structure, deserialised by the same command class that produced it. The gateway of §8 must own that decoding: exposing an opaque serialised blob to a language model and hoping it parses correctly is exactly the failure mode the semantic mapping layer exists to prevent.

The decoded status record carries: application name, FSM state, transitioning, busy, fullyInitialized, an error-reason list, and two timestamps.

Trap: the two timestamps are not interchangeable

The status record carries an information time tag and a wall time, both in nanoseconds. The source is explicit that the time tag "may have no relationship at all with the clock time" — it is a monotonic ordering token, used by the publisher to discard out-of-order updates, not a clock reading. Only the wall time is a real timestamp.

An agent that renders the time tag as a date will produce plausible, precise, and completely fictitious answers to "when did this happen" — the worst possible failure shape for a shifter-facing tool. The framework must expose these as two differently-typed fields and must never let a monotonic token reach a date formatter.

Two details from the publisher affect how the agent should read this. First, the *Args fields are omitted when the argument list is just the command name repeated — so an absent field means "no distinct arguments", not "no data". Second, the publisher drops any update whose time tag precedes the last one written, logging an out-of-order event. IS therefore holds the latest-by-monotonic-tag record, not the latest-by-arrival record, which is the correct behaviour for the agent to assume when reasoning about staleness.

DAQApplicationInfo, at RunCtrl.Supervision.<app>, carries: application name, host, status (the supervision vocabulary of §5), membership, restarting, notResponding, exitCode, exitSignal, and parentName. That parentName field is the cheapest way to reconstruct the control tree from IS alone, without reading OKS.

04

Process Management: the verified data model

Where Run Control owns logical state, Process Management owns the operating-system lifecycle of every TDAQ binary. Its data model is smaller, better documented in-repo, and — as the draft argues — the better pilot for WP3.

4.1 Architecture

The draft's three-component description is verified: clients, a partition-aware server, and root-privileged launchers on each compute node. The naming convention is worth recording because the agent will need it for Tier 3 lookups: a Process Manager server registers in IPC as AGENT_<host full name>.

4.2 The process state machine

Nine states, with both a numeric code and a string form published to IS. Note that the two forms differ in case and spacing — a real trap for string matching.

Table 7 PMG process states. The published string is not the enumerator name
CodeEnumeratorPublished stringMeaning
0NOTAV"not defined"No information available
1REQUESTED"requested"Start has been requested
2LAUNCHING"launching"Launcher started, binary not yet exec'd
3CREATED"created"Process object created
4RUNNING"running"collides Process is alive. Says nothing about data taking.
5EXITED"exited"Exited normally; exit holds the code
6SIGNALED"signaled"Killed by a signal; signal names it. This is the crash case.

Trap: enumerator names and published strings diverge

Four of the nine differ by more than case: NOTAV publishes as "not defined", SYNCERROR as "sync error" (with a space), and FAILED as "failure" (a different word). Any agent tool that filters IS on the state string using enumerator names will silently return empty results for exactly the failure conditions an operator most needs to find. Prefer the numeric state_code for filtering and the string only for display — and put that rule in the semantic mapping layer, not in each agent.

4.3 The PMG Handle, corrected

Processes are addressed network-wide by a URL-style handle. The draft's grammar omits the optional port (F7):

// verified against the handle parser and serialiser
handle   ::= "pmg://" host [ ":" port ] "/" partition "/" application "/" id

host        ::= fully-qualified host name     // non-empty
port        ::= integer                       // omitted when 0 (the default)
partition   ::= partition name                // non-empty
application ::= OKS application name          // non-empty
id          ::= integer                       // disambiguates reuse of the same app name

// examples
pmg://pc-tdq-onl-42.cern.ch/ATLAS/TileCal-RCD/17
pmg://pc-tdq-onl-42.cern.ch:9876/ATLAS/TileCal-RCD/17

Three parser requirements follow from the implementation. The port is attached to the host field and split off after tokenising on /, so a naive split on / yields a host of host:port that will not match anything. The port is suppressed on output when it equals the default of zero, so the same process may be described by two different handle strings — handle equality must be structural, not textual. And every one of host, partition, application and id is rejected if empty, which gives the agent a well-defined validation error to convert into a refusal.

Why the id field decides the PMG response contract

The id exists to disambiguate multiple processes carrying the same application name in the same partition — across restarts and across runs. This is precisely why the draft is right to require a timestamp on every PMG answer. "TileCal-RCD is running" is not answerable; "pmg://…/TileCal-RCD/17 was running as of 03:14:22" is. The framework should make the unqualified form unrepresentable.

The draft proposes classifying every tool as read or mutate. Adopt a four-value taxonomy in WP2 — read read-heavy subscribe mutate — and make the read-only build refuse the last two by construction. Retrofitting this after WP3 means reclassifying every tool in all five agents.

Trap: cumulative counters

utime, stime and the fault counters are monotonically increasing totals since process start. "How did CPU behave over the last hour" requires differencing two samples; reporting the raw value answers a different question, and answers it in units an operator will misread as recent activity. This belongs in the semantic mapping layer as a derived quantity, so that all five agents difference it identically — it is exactly the kind of computation that would otherwise be re-implemented, differently, per agent.

05

The three-vocabulary collision

This finding was not anticipated in the draft, it has no fix at the agent layer, and it determines the shape of the framework. It deserves to be the centre of the architecture paper.

Run Control and Process Management do not share one notion of what a component is doing. They carry three separate state vocabularies, and those vocabularies overlap by name while differing in meaning:

  1. RC FSM state — eleven values, published in RCStateInfo.state. Describes where a node sits in the run lifecycle.
  2. RC supervision status — seven values, published in DAQApplicationInfo.status. Describes Run Control's belief about the process behind an application.
  3. PMG process state — nine values, published in PMGPublishedProcessData.state. Describes what Process Management observes of the operating-system process.
Table 10 Disambiguation table — the seed of the semantic mapping layer
TokenIn RC FSMIn RC supervisionIn PMGRisk if conflated
RUNNING Taking data — (uses UP) Process alive severe A partition can be fully RUNNING in PMG terms with every process alive, and taking no data at all.
ABSENT Default value — means "unknown" No longer running, cause undetermined — severe One means "we have no data"; the other means "it died and we don't know why". Opposite implications for the shifter.
NOTAV — Initial, or PMG unreachable No information available moderate Similar intent, different causes. RC's NOTAV may specifically indicate PMG is unreachable — itself a reportable fault.
REQUESTED — RC asked PMG to start it PMG received the request low Genuinely the two ends of one handshake. Divergence between them is itself diagnostic.
EXITED — RC observed the exit Exited normally, with a code moderate RC's EXITED does not distinguish clean exit from crash; PMG splits it into EXITED and SIGNALED. Answering from RC loses the crash signal.
FAILED — Failed to start Failed to start low Aligned in meaning. Note PMG publishes it as the string "failure".

Why this cannot be fixed at the agent or prompt layer

The obvious response is to tell the model about the ambiguity in a system prompt. That fails for three reasons, and the reasons are worth stating because they are the argument for the whole framework.

  • It is a retrieval problem before it is a generation problem. By the time text reaches the model, a tool has already returned a record saying state: "RUNNING". The ambiguity is in the data, and no amount of prompting recovers a distinction the payload never carried.
  • It multiplies across agents. Five agents means five prompts to keep synchronised against a schema none of them own. The first divergence produces two agents giving different answers to the same question — the exact property the draft rightly calls unacceptable in a shifter-facing tool.
  • It is unfalsifiable at evaluation time. A prompt-level convention cannot be unit-tested. A typed mapping layer can, and its test suite becomes part of the benchmark evidence.

The fix is structural: every state value must be typed by its vocabulary before it reaches the model. The mapping layer emits rc.fsm:RUNNING and pmg.process:RUNNING as distinct values that cannot compare equal. See §8.4.

06

How Run Control and Process Management couple

The draft argues that the coupling between these two services is the strongest justification for an orchestration layer. WP1 confirms this and locates the join precisely enough to build on.

The operational narrative in the draft is verified. On boot, the Root Controller reads OKS for applications and host assignments, delegates process creation to PMG, and receives handles. As each application initialises it registers with the IPC directory; the parent locates it, binds it into the tree, and advances it out of INITIAL. On failure, the launcher detects termination via waitpid, PMG raises an alert, and the parent marks the child bad and halts trigger distribution.

What WP1 adds is the field that makes this queryable. Run Control publishes fullyInitialized — documented in source as "the application has already done the PMG synch". This is the join key between the two services' state models, and it gives the agent a well-defined way to detect the most confusing operational condition in the pair:

The diagnostic that only the orchestrator can make

Consider a node reporting FSM state INITIAL with fullyInitialized = false, while PMG reports its process as RUNNING with a healthy resident set. Neither agent alone can explain this. Together they can: the process is alive and consuming memory, but Run Control has not completed its handshake with it — a hung startup, not a crash, and the remedy is completely different from the one a crash would call for.

This is the concrete form of the draft's "why did TileCal stop?" example, and it is the routing case the orchestration layer must be designed around: not merging two answers, but detecting that two sources disagree and reporting the disagreement as the finding.

Two further couplings are worth recording for WP2:

  • RC's supervision status is derived from PMG, not observed independently. DAQApplicationInfo.status, exitCode and exitSignal are RC's cached copy of what PMG told it. When the two disagree, PMG is authoritative and RC is stale — a precedence rule the mapping layer must encode, because the agent will frequently have both.
  • The Access Manager sits on both paths. RC's refusal vocabulary includes NOT_ALLOWED; PMG's signal exceptions include NOT_ALLOWED_BY_AM. The draft's concern here is confirmed by source: authorisation is enforced per-caller at both services, so a gateway authenticating as a single service account really does erase the per-user accountability the Access Manager exists to provide. This remains an open item for the operations group — but it now has a concrete form, since read-only queries at both services also pass through AM.
07

Access tiers, revised

The draft's three-tier model survives WP1 with one significant revision: Tier 1 is broader than assumed, and the RC/PMG data models are now fully known offline, which changes what has to be sequenced when.

Two revisions to the draft's account:

  • Tier 1 now covers more than the draft assumed. Because the RC FSM, the PMG state machine, the handle grammar, both IS schemas and both IDL surfaces are all recoverable from the repositories, the entire schema of the system is Tier-1 knowledge. Only instance data needs Tiers 2 and 3. The semantic mapping layer can therefore be written and tested in full before any credential arrives.
  • Tier 2 is now the sole critical-path blocker. With F1–F7 resolved, PBEAST credentials and endpoint reachability are the only remaining item that can stall WP2. The draft already ranks this first; WP1's outcome sharpens that to the only thing worth chasing before WP2 starts.

A cheap Tier-2 pre-check, before credentials land

Tier 2's value depends on an assumption no one has yet tested: that the RC and PMG IS classes of Tables 5, 6 and 9 are among the subset PBEAST actually archives. PBEAST stores a subset of operational monitoring data, and nothing guarantees the subset includes them. Verify class-by-class coverage in the first PBEAST session, before building anything on top — if RCStateInfo history turns out not to be archived, the RC agent's "when did this last change state" capability moves from Tier 2 to Tier 3, and the whole sequencing argument changes. This is the cheapest high-consequence check available in WP1.

Methodology: the reusable MCP pattern

WP1's findings are not neutral about architecture. Each one rules something out. This section derives the WP2 blueprint from them rather than proposing it independently — which is also what makes it defensible in a paper.

8.2 The layered architecture

The draft's five-layer stack is sound and survives WP1. What changes is the weight of the semantic mapping layer, which moves from convenience to the framework's principal component, and the addition of an explicit contract boundary above it.

8.3 The generic tool surface

The draft's principle — a small generic query surface plus semantic wrappers, rather than one tool per operation per service — is correct, and WP1 supplies the concrete shape. Because RC state and PMG status are both IS objects differing only by class, one lookup surface serves both.

Following the draft's recommendation, OKS configuration is exposed as MCP resources rather than tools — it is static and addressable, which is what resources are for. WP1 strengthens this: the controller tree and segment membership are exactly the stable, structural content that benefits from being addressable rather than queried, and serving them as resources keeps them out of the tool budget entirely.

8.4 The provenance envelope

This is the mechanism that discharges C1, C3 and C6 together, and it is the piece most worth getting right in WP2 because every later agent inherits it. No value reaches the model bare; each is wrapped with the facts needed to interpret it.

// PMG agent answering: "is TileCal-RCD running?"
{
  "identifier": {
    "kind":   "pmg.handle",
    "value":  "pmg://pc-tdq-onl-42.cern.ch/ATLAS/TileCal-RCD/17",
    "resolved_from": "TileCal-RCD"          // what the operator said
  },
  "values": [
    {
      "field":      "process_state",
      "vocabulary": "pmg.process",             // C1 — cannot compare to rc.fsm
      "value":      "RUNNING",
      "display":    "running",               // the published string (§4.2)
      "means":     "the OS process is alive",  // never "taking data"
      "tier":       2,                          // C6
      "observed_at": "2026-08-21T03:14:22.881Z", // C3 — wall clock, real time
      "age_s":      41.2
    },
    {
      "field":      "cpu_utime_delta_ms",
      "value":      18422,
      "derived":    "difference of cumulative counter over window",
      "window_s":   300,                        // §4.5 — never report raw
      "tier":       2
    }
  ],
  "not_answered": [
    { "question": "is it taking data?",
      "why": "requires rc.fsm vocabulary — route to the RC agent" }
  ]
}

Three properties of this envelope are doing real work, and each maps to a benchmark dimension in the draft's §7:

vocabulary + means
Makes the F8 collision structurally unrepresentable. The model cannot state "TileCal is running" without the qualifier, because the payload never contained an unqualified RUNNING. Feeds correctness.
tier + observed_at + age_s
Every answer is self-dating, so "as of when?" is always answerable and staleness is visible rather than inferred. Feeds correctness and calibrated refusal.
not_answered
An explicit slot for what the agent knows it cannot address, with the reason. This turns calibrated refusal from a prompt-level hope into a schema-level obligation — and gives the orchestrator a machine-readable routing signal. Feeds calibrated refusal directly.

The measurement argument

The draft rightly makes calibrated refusal a first-class benchmark dimension. A schema with a mandatory not_answered slot is what makes that dimension measurable: refusal becomes a structured output to score, not a judgement about free text. This is the strongest available answer to the reviewer question "how did you evaluate refusal?" — and it is only available if the envelope is designed in WP2, before any agent exists.

8.5 The vocabulary registry

The semantic mapping layer's core is a small, testable, declarative registry — not code scattered through the agents. WP1 has produced its first three entries in full: Tables 2, 7, and the supervision vocabulary of §5. Each entry declares, per vocabulary, the token set, the published string for each token, the numeric code where one exists, a one-line meaning, and any collisions with other vocabularies.

That registry is what makes the framework's central claim falsifiable. It supports a specific, cheap test that should run in CI from WP2 onward:

The collision test

For every pair of vocabularies, assert that no bare token from one can compare equal to a token from the other, and that every colliding name has a distinct means string. Seed it with the six collisions of Table 10. Any future service whose vocabulary introduces a seventh collision fails the build rather than shipping an ambiguity — which is exactly the generalisation guarantee WP4 needs to claim.

8.6 How generalisation gets measured

The draft proposes recording framework modifications required by each agent, as evidence for the architecture paper. WP1 lets that be sharpened from a narrative into a metric with a pre-registered prediction — which is a considerably stronger claim to make to reviewers.

Stating the predictions before WP3 turns WP4 into a test rather than a demonstration. It also gives the architecture paper a clean result shape either way: if the RC agent drops onto a PMG-shaped framework with zero envelope changes, the pattern is validated; if it does not, the ledger says precisely where the abstraction failed, which is a publishable finding in its own right.

One caution about the WP3 pilot choice

The draft's case for PMG as pilot — command-shaped, live CORBA interface, publishes to IS, behind the Access Manager, clean identifiers, far smaller state space than RC — is well argued and WP1 supports every premise. Table 8 adds a further point in its favour: PMG's read/mutate split is cleaner, so the read-only boundary can be enforced structurally in the pilot.

The residual risk is the mirror image of the draft's own argument against RC: a framework shaped around PMG's flat object space may fit RC's hierarchical one badly, and hierarchy is the harder problem. Mitigate cheaply — design find_objects and the envelope against both Table 9 and Table 6 during WP2, even though only PMG is built in WP3. The RC schema is already fully known, so this costs design attention rather than implementation time, and it is the one place where WP1's completeness can be spent to de-risk WP4.

8.7 What the harness must capture

The draft's argument that replay is a week-one decision is correct and WP1 adds specificity about what a fixture must contain. Output consistency cannot be measured against a live system, because infrastructure drift becomes inseparable from agent nondeterminism — and §3.5 shows RC's own publisher discards out-of-order updates, meaning the observable IS record depends on arrival ordering the agent cannot control.

A fixture must therefore capture, per snapshot: the OKS configuration in force; every relevant IS object with all attributes; the monotonic time tag and wall time of each record; the tier each value came from; and the vocabulary registry version in force at capture. That last item matters more than it looks — a fixture captured under one registry and replayed under another silently tests the wrong thing, and the failure would look like agent nondeterminism.

The positioning benefit, restated

The draft notes that testing against live Point 1 is prohibited, so "benchmarking on live scientific infrastructure" may not be a supportable claim. WP1 reinforces the alternative framing: reproducible benchmarking against captured production state is both defensible and methodologically stronger, and the fixture contents above are what make the reproducibility claim concrete rather than rhetorical.

9.1 Recommended immediate actions

  1. Chase PBEAST credentials, and nothing else that is externally blocked. It is now the only item that can stall WP2, and the class-coverage check should be the first query run once access exists.
  2. Settle PBEAST ownership with the DCS track this week. Tier 2's promotion to sole blocker makes a duplicated or divergent client materially more costly than it was when the draft was written.
  3. Start the vocabulary registry now. Three vocabularies are fully specified in this report. Encoding them, with the collision test, is unblocked and is the highest-value WP2 work available today.
  4. Fix the target release before writing the registry. Every string in Tables 2, 7 and 9 is release-specific. The registry should record the release it was derived from, so drift is detectable later.
  5. Design the envelope against both schemas. Per §8.6 — cheap now, expensive after WP3.
